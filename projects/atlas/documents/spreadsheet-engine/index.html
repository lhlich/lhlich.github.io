01 / Define the problem

What does a cell mean?

Each address stores raw input: a number, a blank, or a formula beginning with =. A read returns a number or a structured error. Blank cells evaluate to zero, including references to cells that have never been written. Formulas use case-insensitive references and conventional arithmetic precedence.

InputMeaning
12.5, -2e3Numeric literals
=A1 + B1 * 2References and arithmetic: + − × ÷
=-(A1 + 3)Parentheses and unary signs
=SUM(A1:B2, MAX(4, 1), -1)SUM, MIN, MAX; ranges inside function arguments

This is a numeric calculation engine, not an Excel clone. It omits text values, formatting, dates, absolute references, volatile functions, asynchronous formulas, and collaborative editing. Cells use JavaScript numbers, so decimal arithmetic has the usual floating-point rounding behavior.

Write-time versus read-time failure. Invalid syntax and cycles reject the proposed write without changing the sheet. Division by zero is valid syntax: the write succeeds, and evaluating that cell produces #DIV/0!. This distinction makes editing predictable.

      03 / Parse before evaluating

      Turn text into a small language.

      Do not pass formulas to eval. Tokenize the permitted characters, then build an abstract syntax tree with a recursive-descent parser. Each grammar layer handles a precedence level; parsing must consume the complete input.

      expression → product (("+" | "-") product)*
product    → unary (("*" | "/") unary)*
unary      → ("+" | "-") unary | primary
primary    → number | reference | "(" expression ")" | call

      For =A1 + B1 * 2, the root is addition. Its right child is multiplication, so evaluation multiplies B1 by 2 before adding A1. Function arguments can be expressions or ranges. A bare range, such as =A1:B2, is deliberately unsupported because this engine has no array-valued cells.

      Walking the tree also extracts direct dependencies. Expand ranges into cell references and deduplicate the graph edges. Keep the original arguments in the tree: =SUM(A1:A2, A1) must count A1 twice in the sum, even though A1 appears only once in the dependency set.

      Bound the language. This implementation limits formula length to 2,000 characters, tokens to 200, a range to 256 cells, expanded references per formula to 512, stored cells to 512, and dependency paths to 128 cells. These are explicit teaching constraints, not performance claims or a general security boundary.

      04 / Store both directions

      Reads go one way. Invalidation goes the other.

      Keep a forward dependency set for each formula and a reverse set for each referenced cell. If B1 reads A1, then dependencies(B1) contains A1 and dependents(A1) contains B1. Forward traversal evaluates prerequisites; reverse traversal finds everything that may have become stale.

      A1→
      B1 = A1 * 2C1 = A1 + 5
      →D1 = B1 + C1

      Editing A1 invalidates A1, B1, C1, and D1. Reading D1 computes A1 once, because the second branch reuses its cached result. An unrelated D4 remains cached. A set of visited cells keeps the invalidation walk from duplicating work at a diamond's join.

      A formula edit also rewires the graph. Replacing B1 = A1 * 2 with B1 = A2 * 2 removes B1 from A1's reverse set and adds it to A2's. Otherwise future edits would invalidate the wrong cells—or fail to invalidate the right ones.

      Reject a cycle before committing it.

      The engine first parses the proposed input, then validates the graph as if that cell had the new dependencies. A depth-first traversal tracks the active path. Reaching a cell already on that path identifies a cycle; reaching a completed cell does not. Only after validation succeeds does the engine replace the raw input, rewrite edges, and invalidate cached results.

      Validation also checks dependency depth from every stored root, since a change can lengthen an existing dependent's path. This intentionally simple implementation repeats traversal per root. It is easy to inspect, but it is not an incremental cycle detector.

      05 / Decide when to pay

      Lazy and eager share the same graph.

      LazyEager
      On a successful writeInvalidate affected caches.Invalidate, then resolve all affected cells.
      On a readResolve missing prerequisites, cache the result.Usually return the cached result.
      Useful whenMany changed results may never be read.Readers need computed results immediately.
      TradeoffThe first read pays the calculation cost.Writes pay even for results nobody reads.

      Both modes use the same memoized depth-first evaluator. Eager mode asks it to read the affected cells after a write; prerequisites are still evaluated before their consumers. Switching to eager mode resolves stored cells. Switching to lazy mode preserves valid cache entries.

      The workbench renders cached values without calling get. That detail matters: automatically reading every cell after each edit would hide lazy evaluation. “Read all cells” is an explicit read workload, and “Read selected” lets you observe a narrower one.

      Errors participate in the cache.

      Cache a structured error just as you cache a numeric result. If B1 divides by zero, a formula reading B1 propagates the error. A subsequent edit to a prerequisite invalidates both entries, so a new read can recover. Syntax and cycle errors never enter this cache because their writes were rejected.

      Account for the whole edit.

      Let V be the number of cells in the dependency graph and E the number of edges. Finding the affected subgraph costs O(Va + Ea). Resolving a fresh requested subgraph costs its visited cells and edges plus the work in their formula trees. A cached read is a map lookup. However, this implementation's full-graph validation from every stored root can cost O(V(V + E)) per write. Graph invalidation is incremental; write validation is not.

      Excel also maintains dependencies and a calculation chain, marks changed dependents dirty, and orders recalculation accordingly. Its implementation handles a much richer language and calculation model. See Microsoft's explanation of Excel recalculation for that distinction.

      06 / Take it apart

      Run the same engine outside this page.

      Download the files into one directory. The engine works in Node without a package install; it also exposes window.SheetEngine when loaded as a browser script.

      engine.js ↗example.cjs ↗test-engine.cjs ↗
      node example.cjs
node --test test-engine.cjs
      const { Spreadsheet } = require('./engine.js');
const sheet = new Spreadsheet('lazy');
sheet.set('A1', '10');
sheet.set('B1', '=A1 * 2');
console.log(sheet.get('B1'));       // 20
sheet.set('A1', '15');
console.log(sheet.lastEdit.affected); // ['A1', 'B1']
console.log(sheet.get('B1'));       // 30

      The tests cover precedence, ranges, graph rewiring, diamond dependencies, cache preservation, atomic rejected edits, error recovery, mode scheduling, and generated acyclic sheets checked against an independent arithmetic oracle. They verify the implementation's contract; they do not establish compatibility with Excel.

      Extensions worth designing first.

      1. Batch writes. How would you validate a group of edits against one proposed graph and commit all or none? Avoid recalculating intermediate states.
      2. Incremental validation. Can you restrict cycle checks to the proposed cell's prerequisites? How would you still enforce the maximum path length for existing dependents?
      3. Text and typed values. Define coercion rules before adding strings. What does a blank mean inside SUM versus arithmetic?
      4. Structural edits. Inserting a row changes addresses, ranges, and references. Decide whether identity belongs to an address or to a stable cell object.
