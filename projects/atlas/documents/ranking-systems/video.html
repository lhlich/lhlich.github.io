01 · Video / Systems study

Recommend the next video

The next-video rail is a small slate with a large downstream effect. Choosing its first item also chooses the likely autoplay transition, so a strong per-item click predictor can still create a poor session.

1. Define the output and the objective

Assume the product needs five suggestions beside the current video and one autoplay choice. The request includes the current item, coarse language preferences, permitted history, and recent session actions. The desired outcome is a satisfying continuation, with guardrails for unwanted repetition and negative feedback.

Use click, meaningful consumption, explicit satisfaction signals, and dismissals as separate measurements before combining them. A thirty-second watch has different meaning on a forty-second clip and a two-hour lecture. Normalization, clipping, and missing-label rules are product choices that should be documented and evaluated. Never label every unshown video a rejected recommendation.

Scenario assumptions: a large video catalog, a five-item slate, and a 250 ms end-to-end target. The example narrows to 1,000 candidates, scores them, then assembles five. These are design inputs to test, not universal operating points.

2. Separate coverage, scoring, and slate assembly

Begin with a related-item and popularity baseline so the system has a usable path without a personalized model. A learned retrieval model can later map the user/session and videos into compatible vector spaces. Precomputed item vectors make approximate nearest-neighbor search possible; expensive pair-specific features belong in the ranker. The published YouTube recommendation paper is a foundational example of separating candidate generation from ranking, rather than a specification for this scenario.

Combine sources deliberately. If the fresh-content pool is always truncated before ranking, it contributes no cold-start coverage. Track source contribution through every stage. Deduplicate by stable item ID, then inspect near-duplicates at slate assembly.

A tree model with engineered pair features is a useful ranking baseline. A neural interaction model becomes attractive when learned embeddings or sequence context add measurable value. Wide & Deep is one approach to combining sparse feature interactions with learned representations. Choose using quality, serving cost, training complexity, and maintainability on the actual workload.

3. Give each signal an honest freshness contract

Long-term interests can be computed in batch. Recent watched items need a faster update path. An explicit “not interested” action should take effect promptly, including when the learned model is unavailable. Put such controls in a serving-readable suppression store rather than waiting for the next training run.

Use event IDs to deduplicate feedback, event timestamps to define windows, and an explicit policy for late events. Historical features must reflect what was available at the decision time, not just the eventual event time. Late-arriving events can otherwise make offline replay look better than live serving.

Deploy retrieval weights and item-index versions as a compatible pair. Changing one tower can change the geometry of the space; mixing old item vectors with a new query tower needs validation. Keep a rollback pair available, and measure fresh-item reachability separately from average recall.

4. Optimize the slate without hiding the trade-off

Suppose the top four videos are nearly identical clips from one channel. The ranking scores may be correct individually, while the slate wastes positions. A greedy redundancy penalty can make that trade-off explicit:

next = argmax over eligible unselected items i: λ · relevance(i) − (1 − λ) · max similarity(i, selected)

Use comparable score scales, define the empty-slate case, and recompute the similarity term after each selection. This MMR-style heuristic is not a guarantee of satisfaction or fairness. Hard restrictions, such as user blocks, should be enforced independently. Reserve exploration through a separately defined stochastic policy and log its actual selection probabilities; a diversity penalty alone does not create randomized exploration.

5. Check what improved, and who paid for it

Measure candidate coverage, ordering quality on an appropriate judged or mature-label set, and slate-level redundancy. Online, look at satisfaction signals and negative feedback alongside consumption. Track new-item and small-creator exposure without assuming equal exposure is always the correct objective.

A timeout budget includes feature fetches, retrieval, scoring, slate assembly, and headroom. Stage p99 values do not simply add into a measured end-to-end p99. Record the actual request trace and load-test queueing. For a partial retrieval failure, score the remaining eligible pool; if the whole personalized path fails, use a current, policy-checked related-content fallback.

Trace the failure

Fresh videos enter the index within two minutes but receive almost no impressions. Where might they disappear?

Suggested investigation

Inspect retrieval-source quotas, score compatibility across pools, truncation before ranking, missing-feature defaults, and final slate rules. An ingest freshness metric can be healthy even when fresh-item exposure is zero. Add per-stage candidate survival metrics before increasing exploration traffic.

6. A reviewable design

  • One documented label specification, including observation windows and missing outcomes.
  • Candidate-source survival metrics and a quality-versus-cost curve.
  • Versioned retrieval/index compatibility and a fallback that respects user controls.
  • Separate ownership of item scoring, slate restrictions, and exploration policy.
  • A rollout gate with user outcomes, latency, fallback rate, and important segment results.
