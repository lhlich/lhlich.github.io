04 · Search / Systems study

Personalize marketplace search

A user searching for a listing has stated constraints. Personalization should help choose among valid answers; it should not quietly rewrite the trip.

1. Respect intent and availability

Assume a marketplace query specifies destination, dates, party size, and optional price or amenity filters. The service returns ranked available listings. Use personalized history only under the product’s privacy rules, and preserve a useful signed-out experience.

Define which constraints are hard and which preferences are soft. A displayed price ceiling might include fees or only a base rate; get that contract right before ranking. Date availability and capacity are correctness constraints. A past preference for expensive listings is a soft signal that must not override a current explicit budget.

The objective could be a successful booking with low cancellation risk and low search effort. Clicks, wishlists, bookings, and completed stays represent different observation windows. Begin with a clear booking attribution rule and separate long-horizon quality guardrails rather than calling every click a successful match.

2. Retrieve valid candidates, then personalize

Start with structured retrieval and a transparent relevance baseline. A learned personalized retrieval source is useful if it recovers valid candidates missed by the baseline. It cannot create availability. If approximate search is followed by hard filtering, too many retrieved results may disappear; overfetch, filtered indexing, or structured candidate sources are alternative responses. Measure recall on the eligible universe.

A ranker can begin with boosted trees over query–listing features: distance, total-price fit, capacity, and contextual quality. Pair-specific features often provide more value than naming a sophisticated architecture. Consider learned interactions when evidence supports them; DCN-v2 provides one concrete design.

3. Let the session disagree with history

Separate long-term preferences from current intent. A user who usually travels alone may be organizing a family trip. Feed the current query and permitted session state as explicit feature groups, and test cases where they contradict history.

Feature familyExampleFailure to guard against
Listing stateAvailability, current price, capacityA stale prediction offering an invalid result
Historical preferenceTypical budget or property typeHistory overpowering the explicit query
Session stateRecent filters and viewed regionsLate or cross-device actions polluting intent
Query–listing crossDistance or total-price fitTraining features computed with future prices

Log request-time feature versions or reconstructable snapshots. Store event-time and ingestion-time semantics for updates. If a listing price changed after the impression, training must use the old visible price. Merely sharing batch and streaming code does not guarantee identical data availability.

4. Train on observations without confusing them with preference

A booking label is sparse and delayed. Define the unit—query, impression, or session—and deduplicate outcomes accordingly. Several impressions can precede one booking; treating each as an independent conversion can inflate the apparent sample size.

Pointwise prediction and pairwise ordering optimize different things. A within-query pairwise objective can sharpen relative ordering but does not automatically produce calibrated probabilities. If downstream components consume probabilities, evaluate calibration separately instead of assuming that adding a pointwise loss guarantees it.

Position affects observation. An inverse weight is meaningful only when its propensity matches the stated observation or logging model. Adding 1 / position-frequency to every binary label is not a generic unbiased recipe. Define examination assumptions, overlap, and weight clipping; examine variance and sensitivity. See Unbiased Learning-to-Rank with Biased Feedback for a specific formal construction.

5. Cold start needs a route to exposure

A new listing has content and structured attributes but little behavioral history. Give the model valid missing-history defaults, use attribute-based relevance, and ensure a candidate source can retrieve it. Exploration is pointless if retrieval always drops the new listing first.

For a new guest, query intent is already informative. A location-, date-, and price-aware baseline is more useful than global popularity. As the session develops, incorporate fresh signals without requiring a permanent user embedding. Maintain a privacy-compatible option for users who decline personalization.

Slate constraints can promote variety among valid results, but they can also reduce relevance. Specify a policy such as a host cap or a soft redundancy penalty, and evaluate the trade-off. Parity in booking rates alone is not proof of fairness: supply, exposure, relevance, and eligibility differ by segment.

6. Test the whole search journey

Track eligible candidate coverage, ordering judgments, search abandonment, booking completion, cancellation, and result validity. Include cases with sparse inventory, restrictive dates, cold-start guests, and fresh listings. Compare performance at equal candidate and latency budgets.

For a teaching 200 ms target, reserve headroom and measure feature lookup, filtering, model inference, and pagination together. Use a current constraint-aware heuristic when personalization fails. A saved result page must not be treated as an availability guarantee at booking time.

Inspect the hidden failure

The ranker improves offline booking prediction, but restrictive-date queries return fewer useful results. What experiment would distinguish retrieval loss from ranking loss?

Suggested answer

Freeze a set of queries and an eligibility snapshot. Compare recall against a broader eligible reference set before scoring, then compare rankers on the same candidate set. Count candidates removed by date filters and source truncation. The ranker cannot recover candidates it never receives.
