Overview / Systems study

Designing ranking systems

A ranking system is a sequence of decisions about what becomes visible. The right architecture depends on the shape of those decisions: a video slate, a branch of replies, an ad slot, or a page of available listings.

How to read this collection. Start with the comparison below, then read any case independently. The scenarios and numerical examples are teaching assumptions, not reports of any company’s current production architecture. Model names are options to evaluate, not required components.

Start with the decision contract

Before drawing services, write one sentence: given these inputs, return this output, within this deadline, subject to these constraints. That sentence prevents a familiar failure: building an impressive recommender for the wrong product surface.

Separate four objects. The product objective describes the user outcome. The training target is an observable proxy. The serving score combines predictions and constraints. The experiment metric decides whether the change helped. They may be related without being interchangeable. A click label, for example, does not directly measure a satisfying viewing session.

Draw three paths, then connect them

01 / SERVINGRequest → candidates → scores → final outputDeadline, fallback, eligibility
02 / FEEDBACKEvents → deduplication → fresh aggregatesEvent time, late arrivals, privacy
03 / TRAININGHistorical snapshots → labels → model → rolloutLeakage, evaluation, compatibility

The paths meet at a versioned contract: feature definitions, model inputs, index embeddings, policy rules, and event schemas must agree. Record what the server knew when it made a decision. Reconstructing an old impression with today’s availability or tomorrow’s engagement creates leakage, even if the training code is otherwise correct.

For every stage, name an owner, an input/output budget, and a fallback. A fallback must still obey hard constraints. A cached ad can be ineligible; a popular listing can be unavailable. Reliability is returning a valid degraded answer, not merely returning something.

Explore the candidate-cost trade-off

Retrieval determines which items the ranker can ever select. Increasing that set may improve coverage but increases downstream cost. This calculator uses a deliberately simple linear cost model; it does not estimate retrieval recall or hardware performance.

Candidate budget

Assumptions: 80 ms other work + 10 ms ranker setup; 200 ms end-to-end target. Actual batching, queueing, network fan-out, and tail behavior must be measured together.

Make evaluation answer the right question

Use candidate coverage to assess retrieval, judged ordering or mature outcomes to assess ranking, and guardrails to assess the whole experience. A model improvement measured after candidate generation says nothing about relevant items excluded upstream. Report segment results for sparse-history users, new items, languages, and traffic regimes.

Historical exposure selects what gets labels. Logging position is useful context; it is not proof of unbiased learning. Distinguish the probability of selecting an item from the probability of a user examining its position. A correction needs an explicit observation model and assumptions about overlap and confounding. Small randomized interventions can help estimate those quantities, but they must be designed and logged accordingly. Joachims et al. provides a formal learning-to-rank treatment.

Ramp with a rollback plan and compare user-level outcomes with an experiment appropriate to the unit of interference. Changes to a ranked slate can affect later actions; impressions from the same user are not automatically independent samples.

Design exercise

A new model improves ranking NDCG but reduces completion for first-time users. What do you inspect before changing the loss?

Reason it through

Check candidate coverage for new users, availability of session features, score distributions, label maturity, and whether the evaluation population matches first-time traffic. Inspect the final slate and fallback rate. Only then ask whether the target or model is responsible.
